# Run setup

Both `show-your-work` and skills built on it follow this file. Your caller gives the run's kind (`proof` or `explore`), and may give a request folder to add the run to.

- **Skill directory**: in this file, the absolute folder that holds it.
- **Evidence directory**: `<skill directory>/../evidence/`, the `evidence` skill. If it is missing, stop and tell the user to install it next to `show-your-work`.
- **Node**: if `node --version` fails or is below 18, stop and tell the user to install Node.js 18 or newer (https://nodejs.org/ or `brew install node`), then run the skill again.
- **Subagent**, **project folder**, **local host**: as the evidence skill's `SKILL.md` defines them. Read its terms.
- **App repo**: the Code path in `<project folder>/environment.md`, else the repository you were started in. `Code: none` means there is no app repo.
- **Dispatch**: every subagent in the foreground; wait for its report. Never in the background: a headless run ends with your turn. To run subagents in parallel, send their dispatches in one message. If a dispatch still comes back as launched in the background, never end your turn while it runs: your next message is the next step only after its report is in. Headless runs: turn off background subagents where your platform has a setting for it (Claude Code: set `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`).

1. Work out the project folder first: run `node <evidence directory>/scripts/project.mjs <app dir, or none> [<app's main domain>] [--folder <Evident folder>]`, with the app dir and `--folder` as the evidence skill's `SKILL.md` defines them. Use the `Project folder:` it prints. Never another folder, even one that holds an `environment.md`. A `Problem:` line: stop and show it; nothing is written there. Show each `Note:` line to the user. With `Setup shared from:` (a git worktree), `environment.md` and `tester-profiles.json` are linked from the main checkout: its setup holds here too. Then read `<project folder>/environment.md`, never one in the app repo. An existing `environment.md` is only ever added to, never rewritten or replaced. If it is missing, or has no `## Targets` or `## Setup commands`, fill it in with the user from `<evidence directory>/environment-template.md` (auto mode: `AUTO.md`). When App's host is not a local host, ask whether it is a test environment, and stop on anything but yes. On every run, stop if App matches a `Never open` URL. On the first run, ask the user whether to add setup commands. Write only what the user gives you, never a setup command from reading the code. Run the health check, and check that the target serves the build under test (local: rebuilt or restarted; preview: the latest deploy). Follow the evidence skill's `SETUP.md` if `## Evidence` is missing, or a target has no driver (its step 3 says when). For each `## Targets` line a definition matches, check that its target's driver loads (a line no definition matches, which `definitions.mjs <project folder> --list targets` warns about, is not a target of this run: show the warning, never stop or ask for it) (the `check` in its definition, whose path `node <evidence directory>/scripts/definitions.mjs <project folder> --show driver <name>` prints first), read the definition's `## Notes`, and tell the user what they must do. If a target whose `proven-by` is `picture` is text only, repeat its warning: every case of it will be not proven. If the driver drives the user's own Chrome, tell the user that sign-in replaces their session for the app there. If your agent asks before each write outside the working folder, have the user allow the project folder (Claude Code: `/add-dir`), and the browser's download folder when the capture tool saves there (Claude in Chrome).
2. Feature: a short slug for what the run is about. From the folders in the project folder (not `ledger/`, which holds the ledger, or `targets/` and `drivers/`, which hold definitions, and never one of those as a slug), propose one that matches, or a new slug, and have the user confirm it (auto mode: `AUTO.md`). Ledger dir: `<project folder>/ledger/`.
3. Run folder and lock, in one call, never by hand: `node <skill directory>/scripts/run-folder.mjs <project folder> <feature> <request kind> <step>`, with `explore explore` for kind `explore` and `prove proof` for kind `proof`. It makes the request folder `<project folder>/<feature>/<YYYY-MM-DD>-<HHMM>-<request kind>/` and the step in it, and writes the step to `run.lock`. If it prints `Lock: held by <folder>` (exit 2), another run has not finished: it made nothing. A lock whose run's agent is no longer running is taken with a `Lock: taken from <folder>: its run stopped` line: show it. Ask the user whether to wait, take the lock (run it again with `--take-lock`) or stop (auto mode: `AUTO.md`). When your caller gives a request folder, make only the step: `node <skill directory>/scripts/run-folder.mjs --in <request folder> <explore | proof>`. It takes the lock too, unless a step of that request holds it, and prints `Lock: held by` as above (`--take-lock` takes it). The `Step folder:` it prints is the run folder: an `explore` step has `charters/` (the explorers' logs) and `evidence/`; a `proof` step has `sessions/` and `evidence/`. `bugs/` appears with the first bug filed. A `Problem:` line means a target or driver definition could not be read, and the step has no `targets.json`: stop and show it to the user; in auto mode, stop with it. When you finish or stop, release the lock with `node <skill directory>/scripts/run-folder.mjs --release <project folder>`: it deletes `run.lock` and marks the request's page done, so it stops refreshing.

The request's page, `<request folder>/report.html`, is plain HTML that our scripts rewrite as the run goes; while the run holds the lock it refreshes itself every 5 seconds. Point the user at it; never write or edit it.
4. Write `brief.md` in the request folder; with `--in`, in the run folder. It holds only the user's own words and the documents they name (auto mode may add `## Auto mode`: `AUTO.md` §3):
   ```
   ## Request
   <the user's request that started the change, verbatim, if it is in this conversation; else their request to prove it>

   ## To prove
   <what the user asked to have proven, verbatim; your caller may name this heading `## To explore`>

   ## Documents
   - <path of each spec or plan document the user names>

   ## Added at approval
   <each claim the user adds while approving, verbatim; each claim they drop as "Drop <id>: <statement>">
   ```
   The first section is always the user's request. Leave out a section that would be empty.
   **Before you save it, check each line:** can you point to the message where the user said it? If not, delete it, even a helpful aside in brackets.
