# Claim writer: findings mode

With a `Findings:` line, the claims come from bugs, not from a change. Follow `CLAIMS.md` with these changes; section numbers refer to it.

- Write only bug claims, plus the claims the user adds under `## Added at approval`. Propose no changed or retired claims, except a conflicting ledger claim as the last bullet says, and skip §5.
- Read each `bug.json` in the folders it names (a `bugs/` folder, or single bug folders): `title`, `target`, `steps`, `expected`, `actual`, `severity`, `viewport`, and `fix` when it has one. Write one claim per failure, of the behaviour a user would expect, from the brief and the bug's `expected` (often already a claim's sentence), never from the code. Bugs that are the same failure share one claim.
- `source`: `found: <bug ids>`, for example `found: BUG-002, BUG-005`.
- `given` and `viewports` come from the bug: the state it started from and exactly the viewport it failed at. Set `setup` by §7. A `given` that needs a new account of a kind the UI cannot sign up (a plan, a role) needs the setup command that signs one up.
- A claim `fix-claims.mjs` drafted (`"draft": true`) keeps its `id`, `rank`, `status`, `changed`, `source` and `viewports`. Rewrite its `statement`, `given`, `setup` and `cases` by these rules, then delete `draft`. A bug's `steps` are how a tester found it, before any fix: give each case the shortest path to the state its claim needs, and leave out each step that claim does not need (accepting an invite before revoking it), as another fix may have closed that path. A draft that covers several bugs (one patch fixed them) has a case per bug: keep a case for each failure, and merge only cases that are the same failure. `do` names no screen size or device: `viewports` does.
- A bug whose `session` is a charter with profile `bad-actor` (in `charters.json` two folders above its bug folder; read only that file there) gets cases that send to the address its `steps` used, written as the change from a `New accounts` address ("a `New accounts` address with `<b>` before the @"), never as the address itself: claims go to the committed ledger, and `--plan` refuses any email address.
- Test only what the bugs show: no timings, parallel requests or widths they did not use, beyond one control case.
- Rank critical and major bugs `headline`, the rest `routine`.
- If the failure breaks a claim already in the ledger, copy that claim with its id, `fromLedger: true`, `status` `active`, `changed` and `check` null, and no `verdict` (select the ledger as `CLAIMS.md` says, with `--files` the code files the bugs' `source` names); rank it by the bug's severity, set its `source` to `found: BUG-002`, and keep its `files`. Write no new claim for it.
- Conflicts. Compare each copied ledger claim (`fromLedger: true`) with each bug claim and its bug's `fix` (`summary`, `source`, `changesClaims`). They conflict when both start from the same state and the fix changes what a ledger case does or sees there: it disables or hides a control the case uses, or changes or removes text the case expects. A ledger claim a bug's `changesClaims` names conflicts with that bug. After the `--plan` text, return one line per pair: `Conflict: <bug claim id> (<bug id>) vs <ledger id> <case ids>: <what the fix changes, in a few words>; <changed | unchanged>`. Write the ledger claim as changed (`CLAIMS-change.md` §1 bullet 2, keeping its id and `fromLedger`) only when your prompt says `Auto: yes`, or the bug's `fix.source` is the user's words (it starts with none of `broken:`, `gap:` and `auto:`): its cases expect from that state what the bug claim expects, and `changed.why` is `your words: "<that fix.source, verbatim>"`. Else leave it as copied: `unchanged`. This is the only change you make to a copied claim.
