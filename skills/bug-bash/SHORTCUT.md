# Shortcut

Read this only when `start.mjs` says your charter allows a shortcut. `EXPLORER.md` still holds for everything else.

Only when your charter has `groundwork` and `"shortcut": true`. Else reach the groundwork in the app, like any other state.

1. Reach the groundwork state by the cheapest faithful route, the first that fits:
   - API: `## Targets` lists an API and your account's `Sign in:` gives the token or cookie its auth takes. Do the action once in the app and read its request in your network log or your docs. Then send that same request with `curl`, allowed for this, once per remaining repeat, in the `curl` driver's Forms (`node <evidence directory>/scripts/definitions.mjs <project folder> --show driver curl`). It runs the same server checks as the app.
   - Else a setup command from `## Setup commands` that reaches the same state, run as `CAPTURE.md` §4 says, with `<charter id>-groundwork` as its `<claim>-<case>`.
   - Else the app, as usual.
2. Name each call's files `<charter id>-groundwork-<n>-headers.txt` and `-body.txt`. Log each file, and a setup command's file, as `CAPTURE.md` §1 says, with `"role": "measure"`, and the status or exit code in `note`. Log the shortcut as one step whose `action` starts `Shortcut:`; it costs one step of your budget.
3. Check the state in the app (the count it shows). If a call was refused or a count is off, stop the shortcut and repeat that part in the app with full evidence before you file anything. A bug at a step the shortcut skipped is not seen: file only what the app showed you.
4. Do the steps worth testing, the last repeats and what comes after (the 10th and 11th invite), in the app with full evidence, as usual.

`CAPTURE.md` §2 holds for every call: only the API URL in `## Targets` (with none, the App's host), only its email recipients. In the app, act only as your capture rules say. A bug's `steps` start with `Reach <groundwork> (shortcut: <API or setup command key>)`. A replay or another viewport that needs the state again reaches it the same way.
